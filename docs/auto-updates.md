# GitHub app updates

Meshkeep 2.0.4 adds a startup check against the public stable releases at
https://github.com/SUP3RMASS1VE/Meshkeep/releases. The source repository must
remain publicly readable, or the update assets must move to another public
release repository and the build's `publish` configuration must change.
No GitHub token is bundled or required on users' computers.

## User experience

- The installed app checks once after its first window appears. Development
  runs do not check or install updates.
- Newer stable versions show an in-app banner. Downloading requires the user's
  click, shows progress and allows continued work.
- Restart and installation require another click and a confirmation to save
  unfinished edits. Closing the app normally does not install a pending update.
- The header and native menu both provide **Check for updates**. Startup network
  failures stay quiet; manual checks show an error with retry and a release link.
  Releases without update metadata show **Automatic updates are not available yet**,
  rather than suggesting that the internet connection has failed.
- Windows NSIS installations update in place. The bundled Python server is
  stopped before starting the Windows installer so it cannot lock application
  files. The installer preserves the catalogue and preferences.
- Developer ID signed Mac builds use Electron/Squirrel.Mac. Unsigned or ad-hoc
  signed Mac builds can check for newer releases, but use **View release** for a
  manual installation. The application never disables signature verification.

All privileged actions run in Electron's main process. IPC accepts only the
current app's main frame, and exposes no arbitrary download URL or installer path.
`electron-updater` checks package hashes and the applicable platform signatures.
Stable clients ignore prereleases and downgrades.

## Publishing an update

1. Increase the version in `desktop/package.json` and update the lockfile with
   `cd desktop && npm install --package-lock-only --ignore-scripts`.
2. Commit and push to `main`, or push a matching version tag such as `v2.0.4`.
3. Wait for both build jobs and the draft-release job to pass.
4. Review and publish the draft as a normal stable release.

Each release must retain these files (with its own version number):

- `Meshkeep-2.0.4-arm64.dmg` and `Meshkeep-2.0.4-arm64.zip`.
- `Meshkeep-2.0.4-Windows-x64-Setup.exe`.
- `latest-mac.yml` and `latest.yml`, generated by electron-builder.
- Any generated `.blockmap` files, plus `SHA256SUMS.txt`.

The build produces but does not publish its own metadata. The existing release
job uploads all checked assets only after both platforms pass. A published
version is immutable in this workflow; bump the version for another update.
Committing code alone does not make an update available until the draft is
published. Existing releases without manifests cannot supply in-app updates.

Users on 2.0.3 or earlier must manually install a version containing the updater.
The first signed Mac version must also be installed manually by users coming
from an unsigned build. Keep the same app ID and signing identity for later
signed releases.

## Mac signing setup

Add these GitHub Actions repository secrets (do not commit certificates or keys):

| Secret | Value |
| --- | --- |
| `MAC_CSC_LINK` | Base64 of your exported Developer ID Application `.p12`, including its private key. |
| `MAC_CSC_KEY_PASSWORD` | Password used when exporting that `.p12`. |
| `APPLE_ID` | Apple developer account email for notarization. |
| `APPLE_APP_SPECIFIC_PASSWORD` | App-specific password for notarization. |
| `APPLE_TEAM_ID` | Apple Developer team ID. |

With a certificate configured, `electron-builder.mac.cjs` enables signing and
hardened runtime and requires signing to succeed. The Apple account secrets
also enable notarization through electron-builder. Without certificate secrets,
the workflow continues to produce an unsigned Mac build with manual updates.
For local signed builds, use the corresponding `CSC_LINK`, `CSC_KEY_PASSWORD`
and `APPLE_*` environment variables, or `CSC_NAME` with an installed certificate.
Run `./build-mac.sh` so the Mac signing configuration is applied.

## Verification

Run:

```sh
node --test tests/test_updater.cjs tests/test_update_bridge.cjs tests/test_update_ui.cjs
node tests/test_slicer.cjs
node --test tests/test_update_feed.cjs # after npm ci in desktop/
python3 -m unittest discover -s tests -v
```

The real-feed test uses a temporary local HTTP server and synthetic payloads to verify version selection and reject a corrupt download with the actual updater. It never executes an installer. Both GitHub build jobs run it after installing dependencies.

The tests exercise explicit download/install, progress, duplicate requests,
network and verification errors, cancellation, sidecar shutdown, development and
unsigned-Mac behavior, IPC trust checks, and required release assets/checksums.

Before distributing the first update, verify two built versions on Windows and
on a Developer ID signed Mac app: install the older build, publish the higher
version with all assets, reopen, download, restart/install, and confirm the new
version and retained catalogue. Full native installation requires actual release
builds and the signing credentials; mocked tests do not replace that check.
